# 모바일 새로고침 개선 (2026-09-28)

## 확인한 병목

운영 데이터 조회 시 박스 15,797개(박스 JSON 약 7,092 kB), 재고 행 954개(약 1,484 kB)가 있었습니다. 대시보드는 같은 박스를 allShippingBoxes와 activeShippingBoxes 또는 shippedShippingBoxes에 반복 직렬화합니다. 모바일은 매번 모든 박스를 스캔 화면 모델로 생성하고, 대형 JSON 전체를 동기식 localStorage에 저장하려고 했습니다.

## 변경

- 모바일이 요청한 경우에만 `mobile-box-table-v1` 형식으로 박스를 한 번씩 보내고 목록에는 참조 번호를 담습니다. PC와 이전 모바일 요청의 응답 형식은 유지합니다.
- 박스 필드, 출고 완료 박스, QR, 공용용기 제품별 배분·이력을 삭제하지 않습니다.
- 모바일은 확인 중인 스캔과 출고대기 박스만 화면 모델로 생성합니다.
- 재고 캐시는 IndexedDB에 비동기로 저장합니다. 저장소 장애·차단은 실시간 조회를 막지 않습니다. 사용자·환경별 키, 만료, 로그아웃 삭제, 늦은 캐시 응답의 상태 덮어쓰기 방지를 유지합니다.
- 새 형식을 지원하지 않는 서버 응답도 읽을 수 있습니다. 서버를 먼저 배포하고 모바일 파일을 이어서 배포합니다.

## 검증

- 전체 테스트 492개 통과. 마지막 로그인 상태 보호 변경 후 관련 24개 재검증 통과.
- 1,000개 입고 × 16박스 비교 fixture: JSON 9,857,600 → 5,163,464 bytes, 47.6% 감소. 실제 통신 시간이나 실제 휴대폰 속도를 측정한 수치는 아닙니다.
- 실제 로컬 브라우저 IndexedDB: 16,000박스 / 14,729,879 bytes 저장·복원·삭제 통과(전체 약 205ms). 운영 재고 변경 없이 격리된 fixture로 검증했습니다.
- 완료 박스 상태 반영, 수기 수량 보존, 동시 저장 후 늦은 응답 차단, 이전 응답 형식 호환, QR 조회 회귀 검증.

## 재고 조회 서버 지연 추가 수정 (2026-09-28)

모바일 전송량 개선 이후에도 느리다는 운영 보고를 받아 DB 처리 시간을 별도로 측정했습니다.

- PRD 정적 페이지 약 0.26초, 관리자 JS 약 0.29초였으나 기존 `read_dev_inventory_state()`는 `EXPLAIN (ANALYZE, BUFFERS)` 기준 21,525.807ms였습니다. 임시 메모리를 늘려 디스크 임시 쓰기를 없앤 경우에도 15,108.401ms가 걸렸습니다.
- 읽기 전용 `read_dev_inventory_snapshot()`을 추가했습니다. PL/pgSQL에서 `json_agg`와 `json_build_object`로 원본 행을 한 번 구성하여 반환하며, 큰 JSONB 중간 결과를 반복 구성하지 않습니다. 같은 운영 데이터에서 498.371ms였습니다. 이는 DB 조회 시간이며 실제 휴대폰의 화면 표시 전체 시간은 아닙니다.
- 신규 함수 결과의 박스 15,818개, 재고 955건을 원본 테이블과 필드별로 대조했습니다. 개수 일치, 값 차이 0건입니다. 운영 재고 값은 변경하지 않았습니다. 함수 실행 권한은 `service_role`에만 부여했습니다.
- Edge 조회는 재고 버전·QR 갱신 버전·한국 날짜를 확인합니다. 같은 버전의 동시 요청은 한 번만 처리하고 결과는 최대 15초 재사용합니다. 버전 변경, 날짜 변경, 만료, 조회 실패 시 재조회합니다. PC와 모바일의 응답 형식 및 모든 박스 이력은 유지합니다.
- 관리자 화면 시작 시 전체 재고를 미리 조회하던 요청을 제거하고, 생산계획 참조 조회는 생산계획 화면 진입 시 시작합니다.
- 전체 테스트 496개 통과. 서버 캐시 동시 요청, 만료, 실패 후 재시도, 늦은 이전 응답, QR 갱신 및 자정 전환도 검증했습니다.
