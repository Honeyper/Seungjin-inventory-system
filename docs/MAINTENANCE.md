# 구조와 유지보수

## 요청 흐름

```text
PC / 모바일
  ├─ Supabase Gateway ─ 세션 확인 ─ 조회 또는 state-engine 검증
  │                                 └─ 버전 비교 RPC ─ 업무 데이터 + outbox 원자적 저장
  └─ Apps Script ─ 계정 확인 / Drive 첨부

야간 outbox 처리 ─ Apps Script ─ Google Sheets 사본
```

`seungjin-dev-gateway`와 `dev_*` 테이블 이름은 PRD에서도 사용하는 기존 명칭입니다. 이름만 보고 개발 데이터라고 판단하지 말고 프로젝트 ID를 확인합니다.

## 공통 통신 계약

`SeungjinHttp.request(url, options)`는 `{ ok: true, data }` 응답을 반환하고 오류에는 `status`, `code`, 사용자용 `message`를 제공합니다.

- 조회만 네트워크 단절·시간 초과·HTTP 429/502/503/504에서 최대 한 번 재시도합니다.
- 저장·출고·재고조정·로그인·파일 업로드는 자동 재시도하지 않습니다. 응답을 잃어도 서버 처리가 끝났을 수 있기 때문입니다.
- Gateway 조회·저장 제한 시간 45초, 로그인 65초, Apps Script 65초, 파일 업로드 120초입니다. 응답 본문 읽기까지 제한 시간에 포함합니다.
- 동일 세션·동일 payload의 진행 중인 조회만 공유합니다. 변경 요청 시작/종료 시 진행 중 조회의 공유 목록을 무효화합니다.
- 401은 재로그인, 400은 입력값 수정, 409는 최신 상태 확인 후 재시도입니다. DB 내부 오류는 그대로 화면에 노출하지 않습니다.

새 API를 추가할 때 조회인지 변경인지 먼저 구분합니다. 자동 재시도를 변경 요청에 켜지 않습니다. `state-engine.js`에서 의도한 입력 오류는 `ValidationError`, 동시 출고 충돌은 `ShippingStateConflict`로 구분합니다.

## 첨부 파일

`attachments.js`는 이미지 유형·빈 파일·크기를 읽기 전에 검사합니다. 파일 읽기 오류·중단·시간 초과는 폼의 저장 대기를 해제할 수 있도록 reject합니다.

- 명세서: JPEG/PNG/WebP, 512KB 이상에서 긴 변 2,000px·JPEG 0.88로 최적화합니다. 결과가 더 크거나 디코더가 없으면 원본을 유지합니다. 신규/수정 화면이 같은 경로를 사용합니다.
- 제품·불량 사진: 원본을 유지합니다. 제품 이미지의 투명 배경이나 제품 외형은 변경하지 않습니다.
- 입력 파일 읽기와 후속 사진 전송은 각각 최대 2개입니다. 첫 전송은 직렬로 완료하여 배치 내 Drive 폴더 생성 경합을 줄입니다.
- 같은 File/payload와 업무 문맥에 대해 성공한 업로드 결과를 페이지 메모리에 최대 30분, 완료 항목 약 100개까지 유지합니다. 실패한 요청은 캐시하지 않습니다.
- 이는 서버의 영구 멱등성 기능이 아닙니다. 새로고침·새 파일 선택·업로드 응답 유실 후의 중복까지 보장하지 않습니다.

## 주요 업무 규칙

- 재고 정리는 확인/미확인, 자사/사출/인쇄 구분 없이 처리할 수 있습니다. 출고대기는 포함하고 보류·폐기·출고완료는 제외합니다.
- 재고 위치만 수정할 때 기존 박스 수량과 출고 이력을 유지합니다.
- 모바일에서 출고완료 QR을 재등록할 때는 사용자 확인과 실제 수량 검증을 거칩니다.
- 공정은 최대 6도, `processGroups`는 누락·중복 없이 순서대로 묶습니다. 최종공정은 묶음 수가 아니라 전체 도수입니다.
- QR의 PRD/DEV 스타일과 기존 단독 공정 라벨 크기는 별도입니다. 공통 변경 때 두 환경을 각각 확인합니다.

## 검사와 인수인계

`node tools/verify.mjs`는 전체 JS/TS 구문, Node 테스트, diff 공백을 검사합니다. 문법 검사만으로 TypeScript 전체 타입 검사가 수행되는 것은 아닙니다. Edge 배포 시 번들 검증과 응답 확인을 추가합니다.

`tests/helpers/frontend-runtime.mjs`는 실제 프론트 함수를 격리해 실행합니다. 입력/출력·실패 후 상태·중복 저장 방지 등을 검증하고, 소스 문자열만 확인하는 테스트보다 실행 테스트를 우선합니다. 오래된 구현 함수의 존재 자체를 검사하는 테스트는 현재 호출 경로에 맞게 갱신합니다.

PC와 모바일의 큰 화면 파일은 상태·이벤트 결합이 남아 있습니다. 이번 정리에서는 통신·첨부 경계를 분리하고 확인된 미사용 코드만 제거했습니다. 추가 분리 시 화면 하나씩 실행 테스트를 먼저 확보하고 옮깁니다. 스타일의 뒤쪽 선언은 이전 스타일을 덮는 경우가 있어, 비슷한 선택자라는 이유만으로 삭제하지 않습니다.
